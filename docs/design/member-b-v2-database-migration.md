# 成员 B V2 数据库迁移说明

## 1. 当前结论

V2 数据库脚本已经完成并通过 MySQL 8.0.45 临时数据库演练。正式数据库 `special_ed_assistant` 本批未迁移，仍可供旧 V0.3 Java 服务使用。

正式切换安排在 V2 Java 接口具备运行条件后执行，避免数据库先升级导致旧服务无法启动或访问旧表失败。

## 2. 文件用途

| 文件 | 使用场景 | 是否可重复执行 |
|---|---|---|
| `backend/sql/schema.sql` | 全新数据库创建 V2 结构 | 是 |
| `backend/sql/seed.sql` | 本地开发基础字典和演示用户 | 是 |
| `backend/sql/migrate-v2.sql` | 已存在 V0.3 数据库升级到 V2 | 是，成功后由 `2.0.0` 版本标记跳过 |

`seed.sql` 是本地开发数据，会更新 ID 为 `1` 的演示用户和学生。生产数据环境不能直接执行种子文件。

## 3. 迁移保护

`migrate-v2.sql` 在执行任何删除操作前，统计以下旧业务表：

- `observation_session`
- `behavior_record`
- `student_training_plan`
- `teacher_evaluation`

只要任一表存在数据，迁移就以 `SQLSTATE 45000` 中止，并保留旧业务表。当前脚本不猜测旧数据如何映射到新模型，因为旧模型中的频次、A/C code、辅助结果枚举和训练计划单表字段无法无损转换为已确认的新交互。

## 4. 执行方式

### 4.1 全新本地数据库

进入 MySQL 客户端后执行：

```sql
source C:/项目绝对路径/backend/sql/schema.sql;
source C:/项目绝对路径/backend/sql/seed.sql;
```

### 4.2 已存在的 V0.3 本地数据库

先备份，再进入 MySQL 客户端执行：

```sql
source C:/项目绝对路径/backend/sql/migrate-v2.sql;
source C:/项目绝对路径/backend/sql/seed.sql;
```

如果迁移提示旧业务表非空，必须先单独制定数据转换方案，不能绕过保护直接删表。
